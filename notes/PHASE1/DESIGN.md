- 日期：2026-11-03
- 分支：`tianzi-branch`

**1. 目标与范围**

我们在 Colab 的单个 scene 中观察到：有 planning 和无 planning 的 baseline 都在放好第一个箱子后停滞。第一阶段要确认这一现象是否在其他 scene / sampler seed 中重复，并为后续 planner 改进找到依据；目前不能认定两种 baseline 有相同的失败原因。

本阶段只增加记录、视频标注和结果分析，保持 baseline 的动作选择逻辑不变。抓大放小，不安排动作裁剪等细节消融，也不同时调整 horizon、评分、子目标切换或搜索算法。

固定约束：

- 只做 planning，官方 world model 和 policy 权重冻结。
- TA 已确认 subgoal interval 固定为 8 秒；使用提供的 goals 文件。
- 保持环境、相机、控制频率、episode 时长和任务评分不变。
- planner 的输入仍然是图像、提供的子目标和历史执行动作；模拟器的状态及任务信号只进入 evaluator 的诊断记录。

**2. 本阶段要回答的问题**

1. 第一箱放好后，是否开始操作另一个箱子？停滞发生在接近、抓取、抬起还是放置之前？
2. 有 planning 时，active subgoal 是否长期不变，或者一次跳过了多个目标？
3. planner 是否频繁放弃上一轮的后续动作，导致连续执行的动作缺少一致性？
4. 停滞前后，下一帧的预测误差是否明显变化？
5. 模型给出的候选评分是否几乎相同，或一直认为能接近目标，而真实执行没有进展？

这些记录用于提出故障假设。仅凭候选的预测评分，不能判断 policy 是否生成过真正有效的候选；必要时在后续阶段另做保存状态后的候选分支实验。

**3. 对照运行**

先保留两组原始 baseline：

| 配置 | 无 planning：B0 | 有 planning：B1 |
| --- | --- | --- |
| Agent | LatentPolicyAgent | GoalPlanningAgent |
| 每轮候选数 | 1 | 16 |
| 生成长度 | 16 blocks / 8 秒 | 16 blocks / 8 秒 |
| 实际执行 | 1 block / 0.5 秒 | 1 block / 0.5 秒 |
| 去噪 / 积分步数 | 10 | 10 |
| lag | 0 | 0 |
| 子目标阈值 tau | 不适用 | 0.25 |
| 任务 | 4 boxes，最多 1795 control steps | 相同 |

两组使用相同的官方 checkpoint、scene 集合和 sampler seeds。显式指定 world-model 路径，记录实际使用的文件，避免依赖 policy checkpoint 内的旧路径。

执行顺序：

1. 复现 Colab scene 100038，分别使用 sampler seeds 0、2、3，保存两组视频。
2. 增加 10–20 个固定的 validation scenes，包含第一箱前失败、停在一箱、能到两箱及以上的案例；保留完整 scene 清单。
3. 确认日志可解释、找出常见现象后，再扩到固定 50 scenes；本阶段不先跑完整 300-scene 参数搜索。

GPU 和推理 dtype 必须记录。Colab 文档提示 T4 的 float16 结果可能不同，因此不要求单场景视频与 README 演示完全一致。

**4. 常规记录：每个 block 一条轻量日志**

记录频率与现有 agent 调用一致：每 5 个 control steps，即每 0.5 秒一次。

| 类别 | 最小记录内容 | 要回答的问题 |
| --- | --- | --- |
| 时间与任务进度 | control step、仿真时间、当前堆叠数、历史最大堆叠数 | 第一箱之后是否继续进展，是否退步 |
| 子目标 | active index、是否切换、到当前目标的平方距离、对应阈值、停留时长 | 是否追着旧目标不放，或推进过快 |
| 候选选择 | 各候选的终点评分、选中候选索引 | 分数是否有区分度，选择是否持续乐观 |
| 计划连续性 | 本轮执行 block 与上一轮计划中“下一 block”的 RMS 差异 | 重规划是否不断改变接下来要做的动作 |
| 预测一致性 | 上一轮预测的下一 latent 与本轮真实 latent 的 MSE | 预测与真实执行的差异是否在停滞附近增大 |
| 决策耗时 | 本轮 agent.step 的总耗时 | 诊断与后续改进的运行成本 |

候选的最优、次优分数差等摘要从评分数组事后计算，不重复增加很多在线字段。第一版只记录总决策耗时，不拆分每个网络模块的性能分析。

时间对齐约定：

- 每条记录以当前真实图像和该图像对应的仿真时间为基准。
- 子目标字段对应本轮完成切换判断后、真正用于评分的 active subgoal。
- 预测误差比较“上一轮预测的下一帧”和“本轮已经观察到的真实帧”，首条记录为空。
- 计划连续性比较“上一轮准备在现在执行的动作”和“现在实际选中的动作”；不是简单比较相邻两次动作大小。
- 第一阶段固定 execute=1，因此上述比较均对齐一个 block。若未来改 execute，需要重新定义对齐方式。

不能将上一轮的 16-block 预测与之后不断重规划得到的真实轨迹直接比较，并将差异当作长 horizon 的预测误差，因为后续实际执行的动作已经不同。

预测误差只作为整体预测—执行一致性的信号，不独立证明 world model 本身失效。计划变化较大也不自动等于错误，必须结合目标变化、任务事件和视频解释。

无 planning 的 B0 不额外调用 world-model predictor 来补齐日志。其 active subgoal、候选规划成本和预测误差均记为 null；共同的任务进度、计划连续性和耗时照常记录。

**5. 任务事件与“第一箱之后”的分析**

继续复用 evaluator 已有的 stage_steps、first_placement_step、max_placed、final_count、grasp_steps、lifted_steps 和 ground_falls。

增加少量事件记录：

| 事件 | 含义 |
| --- | --- |
| first_box | 第一次达到至少一箱堆叠 |
| second_box | 第一次达到至少两箱堆叠 |
| stack_count_drop | 当前堆叠计数下降，供视频定位 |
| goal_changed | active subgoal 索引发生变化 |
| episode_end | 结束时间、成功状态和最终进度 |

任务事件沿用环境每个 control step 的信号，避免只在 0.5 秒采样点查看任务进度而遗漏短暂事件。计数下降不直接标注为箱子倒塌，需要视频确认。

每个到达第一箱的 episode，事后回答：

- 第一箱之后是否开始接近、接触或抬起另一个箱子？
- 是否持续围绕相同位置运动，或者停在近乎静止的姿态？
- 停滞时 active subgoal 是什么，距离与阈值如何变化？
- 期间是否破坏了已有堆叠？

第一版通过现有任务信号和视频人工标注回答这些问题，不增加物体追踪、检测模型或新的感知模块。

重点汇总：

- 达到至少一箱、至少两箱的比例；保留原来的至少三箱和四箱指标。
- mean peak stacked boxes 与最终堆叠数。
- 第一箱到第二箱的耗时。没有达到第二箱时记为未达成，并记录第一箱之后实际观察了多久，不将其伪装成一次成功耗时。
- 到达第一箱的 episode 中，最终达到第二箱的比例，作为辅助指标；同时报告无条件的一箱、两箱比例，避免忽略分母变化。
- 总决策耗时的平均值与 P95。

**6. 视频与输出**

诊断视频至少显示：

- 当前 front / side 图像。
- B1 的 active subgoal 图像及索引；B0 明确显示无 active subgoal。
- 仿真时间、当前堆叠数、历史最大堆叠数。

每个代表性 episode 配一张简要时间线：任务进度、子目标进度与距离、预测误差及计划变化。重点覆盖第一箱放好前后和最终停滞段。

建议输出到已被 Git 忽略的目录：

```text
outputs/diagnostics/<run_id>/
  run.json
  summary.json
  episodes/
    scene-<seed>.sample-<sample_seed>/
      steps.jsonl
      events.jsonl
      summary.json
      video.mp4
      timeline.png
```

run.json 保存代码版本、checkpoint 与 goals 文件标识、scene 清单、sampler seeds、完整实际配置、GPU、dtype。steps.jsonl 保存轻量标量和候选评分，不常规写出全部候选动作及 latent 张量。

只有少量代表性案例才额外保存完整候选和 rollout，供后续调查；该项不是第一版完成的前提。

**8. 完成标准与后续决策**

第一阶段完成后，应具备：

1. B0 / B1 在相同 scene 和 seeds 下的可复现结果。
2. 代表性 episode 的视频、时间线及第一箱之后的行为标注。
3. 对常见失败模式的证据表，区分已经观察到的现象与尚需验证的原因。
4. 一份简短结论：下一阶段优先做目标 / 评分、warm start，还是候选搜索，而不是同时修改所有模块。

| 主要证据 | 下一阶段优先方向 |
| --- | --- |
| 子目标长期滞留或与实际阶段明显不符 | 子目标切换与目标评分 |
| 计划反复改变，单段动作缺少延续 | 已确认的 warm-start 流程 |
| 预测持续乐观、真实下一帧偏差明显 | horizon 与模型可靠性相关的规划 |
| 候选整体缺少继续操作另一箱的行为 | 进一步诊断候选覆盖，再考虑搜索或采样改进 |

Warm start 的既定方案是：从新的真实观测重新 rollout 剩余计划，用更新后的预测终点 latent 调用现有 policy 采样一个 block 补尾，再与新候选共同评分；该算法改动属于下一阶段，不混入原始 baseline 的诊断运行。
